# LeanCorpus 4.0.0

LeanCorpus 4.0 is the first major release after the 3.1.x line. It adds the Geo and XY shape stack, concurrent indexing and index-inspection tooling, corrects multi-term, phrase and span scoring, strengthens codec, recovery and lifetime behaviour, and deliberately reshapes a small number of public APIs where the previous contracts could not safely support the new behaviour.

### Notes

- .NET 11 includes inbox Zstandard support through `System.IO.Compression`. `LeanCorpus.Compression.Zstandard` still uses `ZstdSharp.Port` on both target frameworks in the current 4.0 code. A follow-up should use the inbox .NET 11 Zstandard implementation on `net11.0` while retaining `ZstdSharp.Port` for `net10.0`, with cross-runtime compression/decompression and index-compatibility coverage. This is planned follow-up work, not an implemented 4.0 change. ([dotnet/runtime #59591](https://github.com/dotnet/runtime/issues/59591))

## Compatibility

- An index records the analysis identity of every analysed field, and `IndexWriter` throws `AnalysisIdentityMismatchException` when a field would be written under a different one: on open for a recorded field, or before a new field is first analysed. A LeanCorpus 3.x index has no recorded identities and its analysis matches no 4.0 identity, so 4.0 refuses to analyse any field into it until it is reindexed or `IndexWriterConfig.AcceptAnalysisIdentityChanges` is set. Changing a field's analyser, or the default analyser, on an existing index now needs the same opt-in. Search and non-analysed fields are unaffected. ([16b4be120](https://github.com/jordansrowles/LeanCorpus/commit/16b4be120fabe1f9fb2734a9087c427433e2fc87))

For the earlier `StemmedAnalyser` behaviour, use `PorterStemmerFilter` or `StemmerAnalyser.Porter()`. ([017824fb2](https://github.com/jordansrowles/LeanCorpus/commit/017824fb200f872ee2ef45ccf91633255ba0a10f))
- `SlovakStemmer` and `AnalyserFactory.Create("sk")` index different terms. ## Added

- Add an opt-in Float32 vector graph (ADR052). A graph that fails its checksum or validation is never used, and a segment too large for one graph array is written without one. With `IndexWriterConfig.BuildHnswOnFlush`, flush builds a deterministic cosine graph (`.vgr`, catalogue role `leancorpus.vectors.graph`) for every unquantised vector field, and every merge rebuilds it. Selection prunes equal-distance ties as Lucene does, so near-duplicate vectors do not densify the graph. Graph distances rank every finite vector as the exact scorer does, including very large and subnormal magnitudes when `NormaliseVectors` is false, and a graph that cannot reach every vector is never written or opened. Vector queries traverse it and rescore the candidates with the exact scorer, so scores match exact search, and they fall back to exact search for selective or empty filters, a hard work budget of about a third of the eligible documents (skipped up front when it would almost certainly be exceeded), an unusable graph, field boosts or a non-positive query boost. `HnswBuildConfig` and `HnswSeed` drive the build; without a seed a fixed default keeps builds reproducible. A segment reader fully validates each graph once and remembers a permanent failure, including a malformed body behind a valid checksum, across evicted reader states. ## Changed

- `IndexSearcherConfig.MaxCachedSegmentReaderBytes` no longer weighs Float32 vector values or vector-graph level zero, which are read through mapped files; `SegmentReaderCacheMetricsSnapshot.MappedVectorBytes` reports them, and `VectorsBytes` now counts only held vector state. A vector segment larger than the budget (about 40,000 1536-dimensional vectors under the 256 MiB default) previously reopened its reader state on every query: on a 553 MB segment graph p95 fell from 11.0 ms to 0.93 ms and allocation from about 3.6 MB to 15 KB per query, and exact vector search stopped reloading too. `MaxCachedSegmentReaders` still bounds the cached states. ([320f550db](https://github.com/jordansrowles/LeanCorpus/commit/320f550dbdf3965a60f9477cd9b9b37e3dd440f7))

# Frozen historical index fixtures

The `.fixture.b64` archives and their manifests are immutable test inputs.
Ordinary tests only read these committed snapshots; they never run a fixture
generator.

The 3.1.1 release and sparse HNSW snapshots are generated by the catalogued
historical project in `src/devops/tests/fixtures/historical`. That project restores only the
published LeanCorpus package pinned by archive and assembly SHA-256, uses an
isolated SDK and package cache, and does not reference current Core source. The
managed command writes new archives and manifests beneath run evidence by
default; an existing output directory is rejected.

```bash
./devops data fixtures --list
./devops data fixtures --version 3.1.1 --scenario sparse-hnsw
./devops data fixtures --version 3.1.1 --scenario migration
```

`data migration-fixtures-311` remains as a deprecated alias for the migration
scenario. See `src/devops/tests/fixtures/historical/README.md` for scenario descriptions,
package-source isolation, archive format and baseline pins.

The migration scenario was deliberately regenerated for ADR043 using the same
pinned 3.1.1 package, SDK and seed. Live document `doc-00` now also contains
`said the government`, demonstrating collapsed legacy stop-word positions before
and after codec migration and force merge. The catalogue, loader and CLI fixture
hash pins were updated together; ordinary tests still never regenerate fixtures.

The migration scenario includes analysed and exact text, empty/small/large/
Unicode stored values, numeric/binary/sorted DocValues with missing values,
legacy Geo points, physical index sorting on `sort:id`, an explicit zero vector,
absent vectors and persisted HNSW membership. The compound generator commits
two deletions in loose segments before using the 3.1.1 assembly's existing
compound packer. Both layouts retain two segments and one committed deletion
per segment. Acceptance preserves `String:sort:id:False` through migration,
independent reopen and force merge, and verifies each layout's complete codec
migration action set.

`pre-v3-bbq-v2.fixture.b64` contains loose and compound BBQ v2 indexes generated
from commit `3dab5b656c0077470cd216646ba085a04fa40ef3` on
`fix/bbq-retrieval-quality`. Its manifest and `fixtures.json` pin the commit,
parent, SDK, runtime, generator source, seed, file list and SHA-256 values. The
fixture includes explicit-zero and absent vectors with persisted HNSW. It
records legacy read and score behaviour only; it does not qualify BBQ v3.

Migration to 4.0 is one way. Current readers support the historical files and
the normal migration framework rewrites supported legacy bodies. Rewritten
stored fields v5, sorted DocValues v3 and float/quantised vectors v2 are outside
the 3.1.1 reader contract. HNSW remains v1. No downgrade tool or promise that
3.1.1 can reopen a rewritten 4.0 index is provided; retain the original index
and use a separate writable migration copy.

## Pre-retirement experimental one-bit BBQ v3

`experimental-bbq-v3.fixture.b64` captures four indexes before product BBQ
writing was retired: loose, compound, mixed BBQ/Int8/Float32 and all-deleted
BBQ. The source is `d2e32814ebbac1c07f097feba6dbee9bebd863f7`; its vector,
HNSW and indexer sources are unchanged from reviewed baseline
`9a93c8199f86371bd70396bc9b0158646544dd64`. The lifecycle checkpoint had not
attached the built-in vector representation policy.

The archive contains its manifest, original input/query vectors, actual Core
assembly SHA-256, 75 physical file hashes and captured search IDs/scores. It
uses 128 dimensions, graph seed 1, explicit zero ordinal 2 and missing ordinal
3. The quantised body is v3 with existing BBQ storage tag 3, retaining its
one-bit interpretation. This fixture proves historical readability, not recall
quality or permission to write. Existing release fixtures and their pins are
unchanged. Tests extract these bytes rather than invoking a retired writer.

Archive SHA-256: `9093003ea1a6c00e2d19f6a46e603762ab4086df9c0a4ce1975f5d12e63f316c`.

`experimental-bbq-v3-legacy-sign.fixture.b64` captures a committed loose index
whose v2 sign-BBQ body was structurally migrated to current `.vq` v3 storage
tag 2 by the preserved pre-retirement Core assembly at commit
`d2e32814ebbac1c07f097feba6dbee9bebd863f7` (assembly SHA-256
`e5255f462bdfb8a870ed8130e43d04503ad95e0c642d6ec755c44c9115cd2fea`). Its
manifest pins all index files and the query score bits before and after the
migration. This supplies a full-index read-only lifecycle input for v3 sign-BBQ;
it does not add a writer path or quality claim. Archive SHA-256:
`9d99f8b29309b3741d8071d99338b5d9f651afb9926b8ba6b3849ad70f75fcbd`.

`experimental-bbq-codec-bodies.fixture.b64` pins 31 pre-retirement bodies used
by decoder, corruption, presence and graph-scoring tests. Its archive SHA-256
is `7fa4fbc127ed0bbb24ea692d6260d84f49e5a6cbf3f04b2b39a31635e68d38b3`.
`experimental-bbq-query-indexes.fixture.b64` retains the original query,
filtering, backup and reader-lifetime inputs, with archive SHA-256
`acda9cbe4d774705f918a3a4f6135be95faf9394d4d9ac674155080e6b0bc41c`.

Both were captured from the preserved pre-retirement Core assembly with SHA-256
`e5255f462bdfb8a870ed8130e43d04503ad95e0c642d6ec755c44c9115cd2fea` on .NET
10.0.14. Their manifests retain source identity, original float inputs, case
selectors and physical hashes. Case selection uses fixed names and dimensions,
rather than hashes of freshly normalised vectors that could vary by platform.
The capture harness and original run logs remain outside the repository.
Test helpers only extract these pinned bytes; a missing case fails without
falling back to a current writer. These archives do not qualify BBQ quality or
new write support.

# Frozen historical index fixtures

The `.fixture.b64` archives and the two `3.1.1-release-*.manifest.json` files
are immutable test inputs. Ordinary tests only read these committed snapshots;
they never run a fixture generator.

The 3.1.1 release and sparse HNSW snapshots are generated by the catalogued
historical project in `src/devops/tests/fixtures/historical`. That project restores only the
published LeanCorpus package pinned by archive and assembly SHA-256, uses an
isolated SDK and package cache, and does not reference current Core source. The
managed command writes new archives and manifests beneath run evidence by
default; an existing output directory is rejected.

```bash
./devops data fixtures --list
./devops data fixtures --version 3.1.1 --scenario sparse-hnsw
./devops data fixtures --version 3.1.1 --scenario migration
```

`data migration-fixtures-311` remains as a deprecated alias for the migration
scenario. See `src/devops/tests/fixtures/historical/README.md` for scenario descriptions,
package-source isolation, archive format and baseline pins.

The migration scenario includes analysed and exact text, empty/small/large/
Unicode stored values, numeric/binary/sorted DocValues with missing values,
legacy Geo points, physical index sorting on `sort:id`, an explicit zero vector,
absent vectors and persisted HNSW membership. The compound generator commits
two deletions in loose segments before using the 3.1.1 assembly's existing
compound packer. Both layouts retain two segments and one committed deletion
per segment. Acceptance preserves `String:sort:id:False` through migration,
independent reopen and force merge, and verifies each layout's complete codec
migration action set.

Migration to 4.0 is one way. Current readers support the historical files and
the normal migration framework rewrites supported legacy bodies. Rewritten
stored fields v5, sorted DocValues v3 and float/quantised vectors v2 are outside
the 3.1.1 reader contract. HNSW remains v1. No downgrade tool or promise that
3.1.1 can reopen a rewritten 4.0 index is provided; retain the original index
and use a separate writable migration copy.

# Frozen release migration fixtures

The `3.1.1-release-loose` and `3.1.1-release-compound` archives contain the
same eight-document corpus generated by the published LeanCorpus 3.1.1 NuGet
package. The adjacent manifests record package and assembly hashes, the pinned
SDK, generation seed, document identities, committed deletions, sparse-vector
membership, query expectations and every physical file hash.

Regeneration is a deliberate maintainer operation:

```bash
pwsh ./devops.ps1 data migration-fixtures-311
```

It requires .NET SDK 10.0.103, PowerShell and Python 3. An offline NuGet source
can be supplied with `-PackageSource /path/to/package/source`. The isolated tool
restores exactly LeanCorpus 3.1.1 and does not reference current engine source.
Its temporary project, package cache and raw output remain under
`artifacts/temp/migration-fixtures-311`. Ordinary tests only read embedded frozen
bytes and require no package download or network connection.

The released compound writer does not correctly persist this corpus's queued
deletions. The compound generator therefore commits the two deletions in loose
segments, then invokes the **3.1.1 assembly's existing compound packer** and
persists the compound flag with that package's segment metadata writer. It does
not construct historical codec bodies using current source. Both layouts retain
two segments and one committed deletion per segment.

The corpus includes analysed and exact text, empty/small/large/Unicode stored
values, numeric/binary/sorted DocValues with missing values, legacy Geo points,
physical index sorting on the real `sort:id` string field, an explicit zero vector, absent vectors and persisted HNSW
membership. Manifest and archive hashes are pinned in the fixture loader;
regeneration requires deliberate review and updating those pins. The released
metadata remains `String:sort:id:False`. Acceptance preserves this exact sort
through migration, independent reopen and force merge, and verifies the complete
codec migration action set for each layout.

Migration to 4.0 is one way. Current readers support the historical files and
the normal migration framework rewrites supported legacy bodies. Rewritten
stored fields v5, sorted DocValues v3 and float/quantised vectors v2 are outside
the 3.1.1 reader contract. HNSW remains v1. No downgrade tool or promise that
3.1.1 can reopen a rewritten 4.0 index is provided; retain the original index
and use a separate writable migration copy.
